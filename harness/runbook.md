# Runbook — operating a project on the harness

Provisional, 2026-11-18. Non-normative how-to. The model lives in
[`workflow.md`](workflow.md), the criteria in [`rubric.md`](rubric.md), the realization in
[`implementation.md`](implementation.md). This document is the operating procedure — what a
person or agent session does, in order.

## Roles

- **Owner** — issues directions, scores and ranks at review, approves prompt amendments, calls
  points of no return.
- **Coordinator session** — the owner's interactive Devin session; runs wherever the owner
  opens it (the **coordinator home**). Applies the gate, drives the cycle budget, drafts
  amendments. The coordinator home is *usually but not necessarily* the project folder.
- **Build session** — a disposable Devin session running in the project folder.
- **JEV session** — a separate `devin -p` invocation per scoring event (see
  `implementation.md`).

## 0. Cold start and intake

A session in any folder may be told "look in `C:\Harness` and set up to run it in this folder"
(or another folder). That folder is the coordinator home; the **project folder is wherever the
owner says it is** — usually the same folder, but not necessarily.

The standing coordinator home is **`C:\harness-ops`** (adopted 2026-11-23): the owner's
interactive session runs there, projects live under `C:\builds`, and deployed harness
tooling lives there. It carries only the direction gate — no builds run in it.

1. Read `C:\Harness\AGENTS.md` (boundaries) and this runbook. Also read the session folder's
   *own* conventions (`AGENTS.md`, rules): if the coordinator home is a durable corpus or doc
   workspace that should not hold incidental machinery — e.g. `C:\Project` — suggest a separate
   build/coordinator folder and take the owner's response before writing `.devin/` anywhere.
2. Work through [`templates/intake.md`](templates/intake.md): **prompt the owner for every
   detail not already stated** — project folder, line name, prompt reference, baseline, first
   direction, judge model. Do not guess.

## 1. Birth a project

The owner names the project folder; the coordinator scaffolds it:

```
<project>/
  .devin/
    hooks.v1.json        # ← templates/hooks.v1.json (both gates)
    direction-gate.ps1   # ← templates/direction-gate.ps1
    check-devlog.ps1     # ← templates/check-devlog.ps1
    jev-prompt.md        # ← templates/jev-prompt.md
    scenarios.md         # intake-derived suite, proposed for owner's approval (H1)
    state.json           # ← templates/state.json — coordinator's externalized state
    register-scan.ps1    # ← templates/register-scan.ps1 — derives register.json
    register.json        # generated by the scan; never hand-edited
    acp-build-driver.py  # ← detached build/JEV spawn (see implementation.md)
    skills/harness/SKILL.md  # ← templates/skills/harness/SKILL.md (global copy also
                             #   lives at %APPDATA%\devin\skills\harness\)
  prompt.md              # snapshot or citation of the prompt revision in force
  devlog.md              # ← templates/devlog.md
  display/               # static shell + emitted data.js — added once the harness-ui
                         #   line ships its first working build (see implementation.md)
  <implementation…>      # created by the first cycle, or copied baseline
```

If the **coordinator home differs** from the project folder, the home may optionally get its
own `.devin/` with only the direction gate (`hooks.v1.json` carrying just the
`UserPromptSubmit` entry + `direction-gate.ps1`) — it receives directions but runs no builds,
so it needs neither the completion gate nor the judge prompt.

The prompt snapshot in `prompt.md` is the revision every cycle in this project answers to,
until a review adopts a new one.

## 2. Issue a direction

Use [`templates/direction.md`](templates/direction.md). Minimum fields: region or variable,
baseline (fresh / modify-and-measure from a named build), cycle budget. Optional: approach
count, criteria to log (default: inherit the previous direction's).

The coordinator clarifies the direction sufficiently. Ambiguous → rejected as inadequate; it
does not run.

The coordinator also verifies **scenario-check coverage**: every scenario the direction
names has a present check or test the build can be enacted against — and, per the
phase-0 contract (`impl-design-001` where adopted), the corpus's completeness is checked
**before a build spawns**: positive checks, negative/discrimination cases, and
module-attached edge cases all present. Where tests are needed and absent, the direction
requires the build to create them — an unchecked named scenario is an adequacy gap,
flagged like an unenacted one at review.

Every derivative doc the coordinator writes carries a `harness-doc` status header
(`workflow.md` §Derivative documents); status transitions are made in the same
edit as the owner action that causes them. The direction gate injects the
register digest on every prompt — pending approvals and the in-force set are
always in view.

## 3. Run a cycle

1. The coordinator **refreshes `prompt.md` at cycle start** — re-assembled from an
   examination of the source documentation, carrying the version preamble (revision
   id, assembly timestamp, assembled-from list, executing cycle) — then **seeds the
   cycle entry** in `devlog.md` — `### Cycle <n>` with the
   direction ref, baseline, prompt ref, criteria, and `**Result:** <pending>` — then
   spawns the build. (Evolved in `C:\builds\project`: the Stop gate blocks while a
   `<pending>` Result stands, so seeding first is what lets the gate work.)
2. Build session in the project folder realizes the entire application per the
   direction — spawned detached via `.devin/acp-build-driver.py` (env: `ACP_CWD`,
   `ACP_PROMPT_FILE`, `ACP_LOG`, `ACP_STATUS_FILE`, `ACP_TIMEOUT`, `ACP_SESSION` to
   resume). The build emits accessible evidence for the named criteria — required by
   the prompt's evaluability paragraph.
3. Score: run the same driver with `ACP_PROMPT_FILE=.devin/jev-cycle-<n>.md` (a copy of
   `jev-prompt.md` with the direction's criteria filled in), or invoke the JEV directly,
   e.g. `devin -p --model <cheap-model> -- (Get-Content .devin/jev-prompt.md -Raw)`.
   Judge model ≠ builder model.
4. Append the JSON verdict to `devlog.md` under a new cycle entry (see
   `templates/devlog.md`).
5. Repeat to the direction's budget. Failed cycles are logged, not auto-retried.

For multi-approach directions, run one build session per approach; each gets its own cycle
entry and verdict.

**Display freshness (owner direction 2026-11-26):** at cycle spawn, start the status
emitter in watch mode — `harness-emit.ps1 -Watch 30` (the deployed copy under the
harness-ui version folder; `-Watch 0` = 30 s default) — so `display/` re-emits through
the build + JEV window instead of sitting stale for the entire build. Stop the watch at
the review point.

## 4. Review point

When the budget is spent: the owner reads `devlog.md`, scores chosen criteria, and **ranks the
project's accumulated candidates**. The coordinator drafts prompt-amendment proposals; the
owner edits and approves them for adoption through `C:\Project`'s revision process. The owner
decides: continue under a new direction, split, or close.

## 5. Point of no return

Owner-directed only. A split is a new start: new project folder (repeat step 1), new
`devlog.md`. A project may keep its own index of lines/variants internally, for reference.
